# 分析说明：地理可达、容量竞争与公平改进

本文说明 `access_data` 的分析口径。资料读取与摘要校验仍按
`docs/data-contract.md`；这里补的是分析层约定，以及哪些结论可以追溯到
哪条登记。

## 1. 两层分析，顺序不能颠倒

**第一层：地理可达（不考虑容量）。** 对每个“居民 × 事项”按门槛求最短
路径。结果只有“有候选网点”或“不可达”，不可达时给出具体原因：

| 原因 | 含义 |
|---|---|
| `unreachable` | 步行/公交网络里都没有到这个网点的有向路径 |
| `mode_not_allowed` | 有路径，但该群体的门槛不允许这种出行方式 |
| `time_threshold` | 最短路径超过该群体该事项的时间门槛 |
| `qualification` | 没有任何网点登记了该事项资质 |
| `closed` | 有资质，但网点开放时段与事项可办理时段没有交集，或到点后已关门 |
| `inactive` | 网点停用 |

缺边、缺方向、班次窗口之外都不补直线距离；路径不存在就是不可达。

**第二层：容量分配。** 只对第一层可达的事项分配容量。分配单位是事项的
“件”，不是人口。

## 2. 需求、人口与份额的分母

- `demands.units` 是事项件数；同一居民两项事项就是两个独立分母。
- `residents.people` 是人数；同一人有多项事项时只计一次。
- `person` 字段标识同一自然人。`person` 重复登记（例如重复列入两个地区）
  在载入时直接拒绝，避免需求被放大。
- 群体分母是 `(area, group)` 的事项件数之和；人口覆盖另算，且只有该人的
  全部事项都办成才计为“覆盖”。
- “事项覆盖”和“人口覆盖”分母不同，报告分表列出，不相互替代。

## 3. 路网与出行方式

- 每种出行方式独立建图。同一方式内可以换乘；跨方式（步行转公交）按
  登记的方向和节点显式连接，不假设任意换乘点。
- `one_way` 只允许 `source → target` 方向；反向没有登记就是不可达。
- 公交按“最早到达”求路：首班前等待、按班距计算下一班、末班后不可乘。
  行程时间 = 到达时刻 − 出发时刻，候车计入出行预算。
- 出发时刻取事项允许的第一个办理日的最早时刻；未登记则用分析入口的
  默认时刻（08:00）。
- 到达网点后，办理时间必须落在开放时段内（按小时粒度），否则该网点不
  计入可达。
- 门槛可以按群体分事项登记，也可以用 `mode_limits` 对步行、公交分别
  设时间上限。

## 4. 能力池、网点上限与整单约束

- 每个网点挂一个 `pool`；`pools.weekly_minutes` 是这组人员的周预算。
  多个网点共用一个池时，池的容量只扣一次。
- 网点自己还可以有 `weekly_minutes`，与池同时生效，取两者中先耗尽的。
- 可分事项（`atomic=false`）允许部分办理，按件分配。
- 整单事项（`atomic=true`）要么全部办成，要么完全不办；不会为了凑件数
  拆成部分办理，也不会把“余量不够整单”误报成已服务。
- 有多个独立事项的居民，每项单独判定；分配结果按事项记录，人口覆盖
  另算。

## 5. 公平目标：两个冻结选项，没有“唯一最优”

| 目标 | 排序规则 |
|---|---|
| `total` | 先最大化总服务件数；同分时按 leximin 改善群体覆盖 |
| `fair` | 先按 leximin 依次改善最差、次差……群体的覆盖率；同分时最大化总服务件数 |

`fair` 采用 leximin 而不是只看单一最差组：当多个群体都为零覆盖时，只看
最差组无法决定先救谁，leximin 会依次改善次差组，同时对最差组不倒退。
`worst` 是 `fair` 的别名。

报告并排给出两个目标的结果。若两者不一致，报告展示交换关系（总量代价
与公平收益），不把任何一方写成唯一正确答案。

## 6. 求解方法与可信度

分配是带容量约束的整数问题。求解器用深度优先分支定界：

- 每个事项的分支为“不服务”“整单放到某个候选网点”“可分时按件分给
  若干候选网点”；同池同速率的网点会去重，避免对称的重复搜索。
- 上界用容量松弛：忽略其他需求对同一池的占用，因此永远不低于真实最优。
- 先用两种贪心构造可行下界，再搜索。
- 有节点预算与时间预算（CLI：`--budget-nodes`、`--time-budget`）。预算内
  搜完标 `exact`（已证最优）；预算耗尽标 `budget_exhausted`，同时给出
  当前最好可行解与松弛上界。
- `exhaustive_optimum` 是独立的、无剪枝枚举，仅用于小网核对。CLI 的
  `--check-small` 会把它与求解器的最优值逐项比较（两种目标都做）；规模
  超出时明确写“跳过”及原因，不用近似值冒充最优。

当前示例网（17 条事项、3 个版本）两种目标都能在节点预算内搜完，并与
独立枚举的结果逐项一致。`tests/test_access.py` 还会把同一套资料复制 14
份（238 条事项）构造大网，用节点预算 3000 触发 `budget_exhausted`，并
断言报告同时给出可行解与不低于它的上界。

## 7. 候选方案：必须整体重算

支持四类调整，都在资料模型上显式表达：

- `open_hours`：追加开放时段；
- `shared_capacity`：合并/共享人员池，或给池增员；
- `new_site`：新增网点，必须指定资质、人员池和上限；
- `new_road`：新增道路/桥，可改变路径和可达性。

每个方案（以及“全部同时实施”的组合方案）都从基线重新求解。组合方案的
效果不等于单项效果相加：共享池会让方案互相挤占。报告给出单项增量、
组合实算和交互项，并列出“谁得到帮助、谁被挤占”。

## 8. 版本保留与变化归因

`data/coordination/versions.json` 按顺序登记版本，每个版本有自己的清单
和摘要；旧版本文件不覆盖。分析入口可以把两个版本整体重算，并列出：

- 道路/班次是否变化；
- 需求是否变化；
- 能力配置是否变化；
- 整体重算后的已服务件数变化。

报告只陈述“哪类登记发生了变化”以及“重算后的覆盖变化”，不把差异直接
当作因果强度。

## 9. 复现

```sh
python tools/build_scenario.py          # 重新生成三个版本（会覆盖生成物）
python -m unittest discover -s tests -v

# 单版本分析，两个目标并排，附小网枚举核对
python -m access_data.cli data/coordination/versions.json analyse \
  --version v2 --objective total --objective fair --check-small \
  --out out/report.md --json-out out/report.json

# 带候选方案
python -m access_data.cli data/coordination/versions.json analyse \
  --version v2 --objective total --objective fair \
  --plans data/coordination/plans.json \
  --out out/report-plans.md --json-out out/report-plans.json

# 版本对比
python -m access_data.cli data/coordination/versions.json compare \
  --from v1 --to v2

# 原有资料检查入口保持不变
python -m access_data.cli data/normal.json
```

`schema 1` 资料没有门槛字段；分析时必须显式给 `--default-threshold`，
否则直接报错，不会默认按无限时间处理。

## 10. 已知边界

- 容量按周汇总，不建模一周内的预约排程；开放时段只用于判定“能否在
  时段内到达并办完”，不用于排队仿真。
- 公交候车按首末班与班距推算，没有实时到站数据。
- 换乘不额外计费时间，也不限制换乘次数。
- 大网不保证最优；报告用求解状态、上界与差距说明近似程度。
- 资料为合成示例，不代表任何现实机构的经营数据。
